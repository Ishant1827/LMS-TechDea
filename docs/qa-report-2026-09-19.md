# QA pass — TechDea LMS

**Date:** 19 September 2026 · **Branch:** `main` @ `cb9251d`
**How:** client (`:5173`) + API (`:5000`) run locally against the Atlas database in
`server/.env`. Every role was driven through the real UI in a browser; access rules,
limits and edge cases were checked directly against the API.

**Test data:** a temporary course, 3 lessons, 1 assignment, 1 quiz, 2 enrolments,
submissions, a doubt, a review and 6 `@example.test` accounts were created and then
**deleted**. The database is back to what it was (8 users, 0 courses).

---

## Short version

The app works. Every main flow — sign up, sign in, author a course, publish, enrol,
learn, take a quiz, submit an assignment, grade it, ask and answer a doubt, manage
users, bulk import — completed end to end with no crash and no console error.

What follows is **11 things that are wrong**, ordered by how much they matter. Four
are real gaps in behaviour, the rest are data hygiene, wording and leftovers.

> **Update — all eleven are fixed.** See *"What the fixes changed"* and the
> sections after it. Nothing from this pass is left open.

## Not working

### 1. Performance page never shows assessment results  ✅ fixed

`server/src/modules/courses/course.controller.js:338` returns `assessments: []`
hard-coded, so the page always shows *"Once this course has assignments or quizzes,
average scores, pass rates and per-student results will show here."*

Seen with a course that had a **published quiz, a published assignment and 4
submissions, 3 of them graded**. The message is not just incomplete, it is untrue — it
tells the teacher the course has no assessments when it has two.

*Fix:* build the aggregation, or change the copy to say the feature is coming. (The
README lists this under "Not built yet"; the screen does not.)

### 2. Deleting a course leaves doubts and reviews behind  ✅ fixed

`course.controller.js:256` deletes lessons, enrolments, assessments and submissions —
but **not** `Doubt` and **not** `Review`.

Verified: deleted the test course, and 1 doubt + 1 review stayed in the database
pointing at a course that no longer exists. The student's Doubts page then shows the
question with a **blank course label** (it does not crash — the client uses `?.`).

*Fix:* add `Doubt.deleteMany` and `Review.deleteMany` to the same `Promise.all`.

### 3. Deleting a user leaves their work behind  ✅ fixed

`server/src/modules/users/user.controller.js:98` deletes only that user's enrolments.
Their **submissions, doubts, reviews and lesson notes** stay. A teacher's grading inbox
will show a submission with an empty name and email.

*Fix:* cascade the rest, or keep them deliberately and render "deleted account"
instead of an empty row.

### 4. "Needs attention" never mentions ungraded work  ✅ fixed

`client/src/features/teacher/pages/TeacherDashboard.jsx:78` builds that panel from two
things only: drafts with no lessons, and published courses with no students.

So a teacher with **a submission waiting to be graded** lands on a dashboard that says
**"All clear — nothing needs your attention right now."** The Assignments page knew the
truth the whole time ("1 Awaiting grade"). The dashboard's four stats have no grading
count either.

*Fix:* add ungraded submissions (and stalled students, already computed on line 77) to
`attention`.

### 5. The README permissions table is wrong  ✅ fixed

It marks browse / enrol / learn / notes / resume / review / ask doubts / submit
assignments as ✅ for **Teacher** and **Admin**. None of that is true:

- every student route is `roles=["student"]` in `client/src/app/App.jsx`, so staff are
  redirected to `/teach`;
- the server agrees — `"Only students can enrol in courses"` (403), `"Enrol in the
  course to ask a doubt"`, `"Enrol in the course to review it"`.

The code is consistent with itself; the documentation is what is wrong. (Teachers do
get **Preview as student** inside the course editor.)

### 6. An assignment cannot be resubmitted  ✅ fixed (teacher-controlled)

A second submit returns `409 "You've already submitted this"` — for assignments as well
as quizzes. One attempt is the documented rule for quizzes; for an assignment it means
a student who pastes the wrong link cannot fix it, and a teacher has no way to send
work back for a revision.

*Fix (if that is not intended):* allow re-submission until the due date, or add a
"return for revision" action that clears the submission.

### 7. Date-only due dates show a wrong-looking time  ✅ fixed

The builder takes a **date**; the assignment page renders *"due Oct 15, 2026, 5:30
AM"*. The date is stored as midnight UTC and printed in local time (IST = +5:30).
Nobody set 5:30 AM.

*Fix:* render date-only dues without a time, or store the end of the chosen day.

### 8. Reading lessons are plain text only  ✅ fixed

A reading lesson containing `**Bold**` shows the asterisks literally. No markdown, no
HTML, no lists — only line breaks. Defensible as a decision (it is also why there is no
XSS hole here), but the field is labelled "Reading text / post" and teachers will
expect formatting.

### 9. `npm run backfill:verified` is broken  ✅ fixed

`server/package.json` declares it as `node scripts/backfill-verified.js`, and
`server/scripts/` **does not exist**. Left over from the removed email feature.

*Fix:* delete the script entry.

### 10. Lesson reorder accepts a wrong payload silently  ✅ fixed

`PUT /api/courses/:id/lessons/reorder` reads `req.body.orderedIds`. Send any other key
and it returns **200 with the lessons unchanged** — the caller gets a success it did
not earn. (With the right key it works: a full reverse and restore were verified.)

*Fix:* 400 when `orderedIds` is missing or not an array.

### 11. Two small README inaccuracies  ✅ fixed

- "Imports run in chunks of **50**" — the client sends **25** (`BulkImport.jsx`,
  `CHUNK = 25`); 50 is the server's per-request cap.
- "**No file uploads anywhere**" — the course editor has a thumbnail image picker. It
  never uploads: the browser resizes the image and stores it as a `data:` URL on the
  course document (a 1200×800 PNG became a 6 KB JPEG). True in spirit, misleading as
  written.

## What the fixes changed — 19 September 2026

Findings **1 to 4** are fixed and re-tested on a freshly seeded course (2 students,
2 assessments, 4 submissions, doubts and reviews from both). Everything was removed
again afterwards; the database is back to 8 users and nothing else.

**1. Performance now reports real numbers.**
`performance` reads the course's assessments and submissions and returns, per
assessment: submissions, graded, average score and pass rate. A quiz score is already a
percentage; an assignment score is converted from its `points` scale. Unscored
submissions are counted but **left out of the average** rather than treated as zero,
and the table prints `—` instead of `0%` where nothing has been scored yet. A pass rate
is shown **only for quizzes** — an assignment's `passPercent` is a schema default of 60
that no screen ever asked the teacher about, so reporting against it would be a number
nobody chose. The old "once this course has assignments or quizzes" card now appears
only when the course genuinely has none.
Verified: quiz 100% + 50% → avg **75%**, pass rate **50%** at a 60% mark; assignment
15/20 with one ungraded → 2 submissions, 1 graded, avg **75%**, pass rate **—**.

**2. Course delete takes doubts and reviews with it.**
Added to the same `Promise.all`. Verified: a course with doubts and reviews from two
students left **nothing** behind.

**3. Account delete takes that person's work with it.**
Enrolments (which carry their notes), submissions, doubts and reviews. Answers they
wrote *as a teacher* stay, because the doubt belongs to the student who asked it. The
bulk-delete toolbar had the same omission as a separate copy of the code — both paths
now call one helper, `removeUserAndTheirWork`, so they cannot drift apart again.
Verified: deleting one of two students removed exactly that student's rows.

**4. "Needs attention" leads with work waiting on the teacher.**
New endpoint `GET /api/submissions/pending` (teacher/admin) returns ungraded
submissions grouped by course — their own courses, or every course for an admin. The
dashboard now lists *"N submissions waiting to be graded"* first, then stalled students
(a count it was already calculating and never showing), then the two course warnings it
had before. Each row links where the work is: grading to Assignments, stalled students
to the roster, course problems to that course. If that check fails to load, the panel
says so instead of claiming "all clear".
Verified: with 1 ungraded submission the dashboard reads *"QA Fix Check — 1 submission
waiting to be graded"*; once nothing is pending, "All clear" returns.

**Also updated:** `README.md` (the stale "not built yet" line, the new endpoint, the
performance endpoint's description) and `docs/security.md` (rule **R14** — a delete
takes everything that pointed at what was deleted — plus a change-log entry and a new
verification date).

`vite build` is clean. Findings **5 to 11 are untouched** and still open.

## Fix for finding 6 — "Send back", teacher-controlled

Chosen deliberately over letting students edit their own work: **a student can
still neither edit nor withdraw a submission.** The only way one reopens is a
teacher sending it back, so every reopen is a deliberate act with a reason
attached.

**Teacher.** A **Send back** button sits next to Save in the submissions inbox.
It refuses to fire without a note — "do it again" with no reason is not feedback
— and asks for confirmation, showing the note that is about to be sent. The row
then reads `returned`, the button disappears, and a line says when it went and
that it is waiting on the student. The inbox grew a **Sent back** figure, and
"To grade" now counts only work actually waiting on the teacher.

**Student.** The assignment returns to **To do**, tagged **Sent back**. Opening it
shows a banner — *"Your teacher asked you to redo this"* — with the teacher's
note under it, and the form reopens **pre-filled with what they wrote last
time**, so fixing one broken link is not a retype. The button reads **Submit
again**.

**Rules enforced on the server**, each one tested:

| Rule | Result |
|---|---|
| Send back with no note | `400 — Say what needs changing before sending it back` |
| Send back a **quiz** | `400 — a quiz can't be sent back` (its answer key is already revealed, so a retake would be a free mark) |
| Send back the same one twice | `409 — already with the student` |
| Send back something already **graded** | allowed — and the score is cleared, so no mark ever stands on work that has since changed |
| Student resubmits after a return | accepted — same record updated, so one row per student still holds |
| Student resubmits **without** being sent back | `409 — You've already submitted this`, unchanged |
| Returned work in the teacher's "to grade" queue | excluded — it is the student's move, so it must not sit in the teacher's pile |
| No token | `401`, ownership check unchanged |

Full round trip driven in the browser: wrong link submitted → teacher sends it
back with a note → student sees the note and resubmits with the right link → it
lands back in the teacher's queue as "to grade". `vite build` clean.

## Fix for finding 7 — a due date now carries a time, in IST

**The rule:** a deadline is one instant, and that instant is Indian time. It reads
the same to a teacher in Pune and a student whose laptop is set to New York.

**Teacher.** The builder's due field is now a **date and time** picker, labelled
*(optional, IST)*. Picking only a date fills **23:59** automatically, so "due
Oct 15" still means all of Oct 15 rather than the first minute of it — and the
teacher can change it to any time after that, midnight included. The assignments
table shows the time alongside the date, because a deadline nobody can see the
time of is one somebody will miss.

**Student.** The assignment page reads *"due Oct 15, 2026, 5:00 PM IST"*. The
zone is spelled out on screen: a time with no clock attached is a time somebody
gets wrong.

**What was actually broken.** `<input type="date">` hands over `"2026-10-15"`, and
`new Date("2026-10-15")` is defined to mean midnight **UTC**. Printed back in
local time that is *5:30 am* — but the display was the small half. `isOverdue`
compares against the same instant, so a student submitting at 10 am on the 15th
was already **overdue on the day the work was due**. On a negative UTC offset the
assignment showed the **wrong day** entirely (`Oct 15 00:00Z` is Oct 14, 7 pm in
New York).

**What changed:**

| Where | Change |
|---|---|
| `client/src/shared/lib/assessments.js` | `fmtDate` / `fmtDateTime` render in `Asia/Kolkata`, and `fmtDateTime` appends **IST**. New `istInputValue` / `istToInstant` convert between the picker's `"YYYY-MM-DDTHH:mm"` and a real instant at `+05:30`. `dueLabel`'s day counting moved onto IST calendar days. |
| `TeacherAssignments.jsx` | `type="datetime-local"`, the 23:59 default, the value converted through `istToInstant` on save, and the list row switched to `fmtDateTime`. |
| `assessment.controller.js` | `parseDueAt` — a bare `"2026-10-15"` from a direct API call becomes the **end** of that day in IST, and anything unparseable becomes `null` instead of an `Invalid Date` that would fail at save time. |

`isOverdue` itself is unchanged. It always compared real instants correctly; it
was simply being handed the wrong one.

**Verified** (helpers driven directly):

| Input | Result |
|---|---|
| Teacher picks `2026-10-15T17:00` | stored `2026-10-15T11:30:00.000Z` |
| That instant back into the picker | `2026-10-15T17:00` — no drift on edit |
| Shown to a student | `15 Oct 2026, 5:00 pm IST` |
| `parseDueAt("2026-10-15")` | `2026-10-15T18:29:59.999Z` = 23:59:59.999 IST |
| `parseDueAt("rubbish")` / `istToInstant("not-a-date")` | `null` |
| Due 5 minutes ago | "overdue", `isOverdue` true |
| Due in 3 days | "due in 3 days", `isOverdue` false |

India has no daylight saving, so the fixed `+05:30` offset is exact and the day
arithmetic needs no rounding. `vite build` clean (1642 modules).

**And the deadline is now enforced**, decided alongside this fix — see below.

**Now open:** **8** (reading lessons are plain text) and **10** (reorder accepts a
wrong payload).

## Deadlines are now enforced

A due date the server never checked was decoration: late work was accepted and
merely labelled *overdue*, and anyone with `curl` could ignore it entirely.
`POST /api/assessments/:id/submit` now refuses it.

**Student.** Past the deadline with nothing handed in, the form is gone. In its
place: *"This closed on 15 Oct 2026, 5:00 pm IST — ask your teacher to extend it
if you still need to hand this in."* The form is removed rather than disabled,
because a form you can type a full answer into before being told it is too late
is worse than no form at all.

**Teacher.** Two things reopen a closed assessment and both are theirs: **moving
the due date** (reopens it for the class) and **sending a submission back** (that
one student, and it stays open past the deadline because reopening it was the
teacher's deliberate act). A student can never reopen their own.

**A timed quiz can't outrun its own deadline.** The countdown starts at whichever
is smaller — the time limit, or the time left until close. A 30-minute quiz opened
five minutes before the deadline gets five minutes and auto-submits while the work
is still accepted, instead of running its full half hour and being refused at the
end with a completed paper inside it.

**One minute of tolerance** sits on the server check, for the gap between a
student's device clock and the server's. It is skew, not leniency: the screen and
the countdown both show the real deadline.

**Verified** — the decision branch driven across every combination:

| Situation | Result |
|---|---|
| An hour before the deadline | accepted |
| One second before | accepted |
| 30 s after (inside the skew tolerance) | accepted |
| 2 minutes after | `400 This closed on 15 Oct 2026, 5:00 pm IST` |
| A day after | `400` — same message |
| Assessment with no due date | accepted, any time |
| A day late, but the teacher sent it back | **accepted** — their call, not the student's |
| A day late, already submitted | `409 You've already submitted this` (unchanged) |

| Quiz opened | Countdown starts at |
|---|---|
| 2 h before close, 30 min limit | 30m 00s |
| 5 min before close, 30 min limit | **5m 00s** |
| 40 s before close | 40s |
| No due date, 30 min limit | 30m 00s |

`vite build` clean; the server module loads. Not driven through the live UI —
that needs a signed-in teacher and student against the Atlas database, which this
session has no credentials for.

## Fix for finding 8 — reading lessons can be formatted — 20 September 2026

**The choice.** Three options were on the table: rename the label so nobody
expects formatting, a toolbar of buttons, or a Word-style editor. The toolbar
was rejected on use: a teacher writing a whole lesson would be stopping to
select and click for every bold word, which is fine for a note and miserable for
a lesson. A Word-style editor was rejected on risk — it stores HTML, which puts a
sanitiser on the only path between a teacher's keyboard and every student's
browser, and that sanitiser becomes the thing standing between this app and an
account takeover (§4.1).

What shipped is the third thing: **the teacher types continuously, and a handful
of symbols mean something.** Nothing interrupts them, and nothing they type can
ever become a tag.

**What a teacher can write**

| Type this | Students see |
|---|---|
| `# Chapter 1` | a big heading |
| `## Part 1` | a smaller heading |
| `**important**` | **important** |
| `*a note*` | *a note* |
| `- first point` | a bullet |
| `1. first step` | a numbered step |
| `[TechDea](https://techdea.in)` | a clickable link |
| ````code```` | `code` in a box |
| three backticks on their own line | a block of code, until the next three |
| `---` | a dividing line |
| a blank line | a new paragraph |

A bare `https://…` becomes a link by itself. Everything else stays exactly as
typed.

**Instructions, in the teacher's words.** Under the box, always visible: *"Just
type normally. A blank line starts a new paragraph. A few symbols add formatting
— Preview shows exactly what your students will see."* Below that, a collapsed
**"How to add headings, bold text and lists"** opens a two-column table —
*Type this* / *Students see* — whose right-hand column is rendered by the same
component the student page uses, so the instructions cannot drift from the
behaviour. A **Write / Preview** switch sits beside the label; Preview is the
real student rendering, not an approximation.

The same editor is used for a video lesson's description, which renders through
the same component.

**Why this is not a new XSS hole.** The renderer
(`client/src/shared/lib/markdown.jsx`) builds **React elements**, never an HTML
string, and `dangerouslySetInnerHTML` still appears nowhere in the codebase. A
teacher's `<script>` is escaped text on the page — the same guarantee the plain
`<div>` gave before. Links are the one place authored text reaches an attribute,
and they go through the existing `safeUrl`. Written up as control **V5** and rule
**R17** in `docs/security.md`.

**Verified** — the renderer driven directly, output shown as rendered HTML:

| Input | Output |
|---|---|
| `<script>alert(1)</script>` | `&lt;script&gt;alert(1)&lt;/script&gt;` — text |
| `<img src=x onerror="alert(1)">` | escaped, no tag |
| `[click me](javascript:alert(1))` | `click me` — plain text, no link |
| `[click me](data:text/html,…)` | `click me` — plain text, no link |
| `[click me](vbscript:msgbox(1))` | `click me` — plain text, no link |
| `# <b>not bold</b>` | a heading containing escaped text |
| `[Python](https://en.wikipedia.org/wiki/Python_(programming_language))` | a correct link — brackets inside a URL survive |
| `Go to https://techdea.in.` | link to `https://techdea.in`, full stop left in the sentence |
| An unclosed code fence | closes at the end of the lesson rather than eating the page |

Headings, bold, italics, bullets, numbered lists, paragraphs, line breaks, inline
code, code blocks and dividers were each checked the same way.

**Seen in a browser:** the teacher's editor and the student's page side by side,
Write and Preview both, the guide table open. No console errors. `vite build`
clean, 1644 modules, **+3.8 KB gzipped and no new dependency**.

**One consequence.** Lesson text written before today is now interpreted. A stray
`#` or `*` at the start of a line in an old lesson would render as a heading or a
bullet. The database holds 0 courses, so nothing is affected — this would have
been a migration if it had waited.

**Then only 10 was left** — fixed the same day, below.

## Fix for finding 10 — reorder answers for what it did — 20 September 2026

`PUT /api/courses/:id/lessons/reorder` read `req.body.orderedIds`, fell back to
an empty list when it was missing, wrote nothing and returned **200 with the
lessons unchanged**. A caller with a typo in the key got a success it had not
earned, and would have kept getting one.

Fixing only that would have left a second, quieter version of the same bug
next to it. A list naming *some* of the lessons was also accepted: the ones
left out kept their old `order`, so the curriculum came back interleaved and
the reply still said 200. So the rule is now the whole set —

**`orderedIds` must be a non-empty array naming every lesson of the course,
exactly once.** Anything else is a 400 that says which way it is wrong.

A useful side effect: because the ids are checked against the course's own
lessons before any write, nothing unrecognisable ever reaches `updateOne`. The
old code would have passed a malformed id straight to Mongoose and taken a cast
error *after* reordering some of the lessons.

The client already sends the complete flat list on every move, so nothing on
that side changed.

**Verified** — the validation driven exactly as the controller runs it, against
a course of three lessons, with the two database calls stubbed so no live data
was touched:

| Sent | Result |
|---|---|
| `{ orderedIds: [c, a, b] }` | **200**, order written `c=0 a=1 b=2` |
| `{ ids: [c, a, b] }` — the finding | `400 orderedIds must be a non-empty array of lesson ids` |
| `{}` | 400, same |
| `{ orderedIds: "a,b" }` | 400, same |
| `{ orderedIds: [] }` | 400, same |
| Only two of the three lessons | `400 must list every lesson in this course, exactly once` |
| The same lesson twice | `400 lists the same lesson twice` |
| A lesson from another course | 400, exactly-once |
| An extra id on the end | 400, exactly-once |
| A malformed id | 400, exactly-once — and no write happens |
| `{ $ne: null }` where an id should be | 400, exactly-once |

Written up as control **V17** and rule **R18** in `docs/security.md`.

## The pass is closed

All eleven findings of 19 September are fixed. Four were real gaps in
behaviour, and all four turned out to hide a second instance of themselves —
a delete path duplicated in the bulk toolbar, a deadline that was never
enforced, a partial reorder accepted as silently as a mistyped one. Each is
recorded above with what was verified.
